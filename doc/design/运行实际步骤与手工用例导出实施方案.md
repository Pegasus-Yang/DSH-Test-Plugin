## 1. 用户最终看到什么

最初规划保留“搜索 agent 关键字”。模型看到真实页面后，将实际需要的操作逐条说明并执行，例如：

| 序号 | 实际步骤 | 来源规划步骤 |
| --- | --- | --- |
| 1 | 点击页面顶部的搜索按钮，展开关键词输入区域 | 搜索 agent 关键字 |
| 2 | 在搜索输入框中输入本次关键词；输入内容：`agent` | 搜索 agent 关键字 |

如果实际还需要按 Enter 提交搜索，就再保存“3. 按 Enter 提交搜索”。如果页面本来就有搜索框，则不会编造“点击搜索按钮”。上述为说明粒度的示例，不固定某个网站必然需要哪些操作。

测试结束后，报告中的每个用例实例提供带序号的“实际步骤”，展示操作说明、真实输入、执行状态和关联检查。用户可以下载 Markdown 手工用例和 JSON 步骤数据，保存后参考执行或继续编辑。

原始任务、规划步骤、运行定义和既有断言保留。新增记录说明“这次具体怎样操作”，不会把原规划替换成另一套执行计划。

## 2. 首版建议范围与成功标准

建议首版默认随测试启用，不增加设置开关或斜杠命令；仍只使用 `/test`、`/test-plan`、`/test-run`、`/test-data`。

必须做到：

1. 规划后，随着当前页面或接口情况逐步记录真实操作说明；不在规划期预先编造整份操作清单。
2. 一条说明能够关联当前运行、数据实例、规划步骤和实际工具调用；序号由程序生成。
3. 正常浏览器交互尽量一条记录表达一个可由人执行的动作。例如点击与输入分别记录。
4. 报告中展示实际顺序；重试不覆盖旧记录，失败、拒绝和未知结果不冒充已完成操作。
5. 手工用例保留实际操作、数据和原有预期；预期没有定义时标明待补充，不根据实际页面倒推预期。
6. JSON、Markdown、报告和重建结果来自同一份已保存数据；重建不调用模型、访问目标或补执行。
7. API 用例记录请求与检查，不出现浏览器步骤或媒体占位；CSV 多实例分别保存，不串数据。

本次不扩展为无模型回放、自动脚本生成、用例校准、测试管理平台上传或 App 执行适配。导出的 JSON 是实际步骤记录，不是现有 `/test-run` 的可执行 JSON 计划。

## 3. 当前代码已经有什么，还缺什么

| 当前机制 | 已确认的能力 | 本次需要补齐 |
| --- | --- | --- |
| `text-plan.ts` 与 `plan.json` | 规划保存业务短句及文字检查点 | 增加独立的实际操作记录，保留规划与操作之间的映射 |
| `test_define_step` | 当前步骤运行时确定能力、目标及原因 | 不把这个宏观定义误当作每个点击、输入的说明 |
| `CallRecord`、`NativeTest.bind/settle` | 按调用 ID 保存参数、时间、结果和实例绑定 | 将面向用户的操作说明与具体调用绑定 |
| `test_capture`、`capture_attempts` | 保存采集位置、原因、可信观察与证据 | API 请求和必要采集可以复用原因及调用信息 |
| `tools/pre-execute`、`tools/execute`、`tools/result` | 观察同一 Agent 的准入、派发与结算 | 区分操作提案、进入派发通道、结果及未获确认的动作 |
| `Recorder`、`rebuild` | 事件账本、原子快照、脱敏与只读重建 | 保存新增字段，并生成实际步骤与手工用例文件 |
| `report.ts`、`report-client.ts` | 按实例展示步骤、断言、附件、录像 | 增加有序实际步骤及下载，处理旧记录和不同实例的切换 |

当前 `assistant/message` 观察主要用于确认计划通报；插件并未把执行阶段的自然语言解释整理为可逐项关联的操作列表。因此，仅增加报告中的一段总结，不能保证拿到真实、完整、顺序正确的操作步骤。

已核对公开 SDK：工具参数与调用身份在原生管线中受保护，`tools/execute` 包装只能按协议处理取消信号，不能偷偷给已有 MCP 调用添加说明字段。现有 `NativeTest.call()` 已通过相同 Agent、`rootCallId`、`parent` token 和取消信号调用原工具，可作为本次转交操作的复用入口。

## 4. 三种实现方式与推荐选择

| 方式 | 优点 | 对当前需求的不足 |
| --- | --- | --- |
| 根据工具名称和参数自动生成说明 | 不需要额外的模型说明 | `element` 可选、`ref` 不可供人复用；参数翻译缺少业务目的，也难处理复合脚本 |
| 结束后让模型总结全部真实步骤 | 对现有运行入口影响小 | 可能遗漏、合并、调换顺序，难区分未执行提案与真实调用；重建还可能依赖模型 |
| 同一次操作携带简短说明，再转交原工具执行 | 说明与调用在执行前绑定，原生结果可关联；不需要另一次“登记说明”模型轮次 | 需要给当前测试增加一个内部工具，保留好原生错误、审批及多模态结果协议 |

**推荐第三种。** 在当前测试作用域注册内部工具 `test_execute_operation`，用于有业务意义的浏览器交互。它不是新斜杠命令，也不是独立执行器；登记说明后复用 `NativeTest.call()` 转交原有工具。

“操作解释”指面向用户的简短说明，写清对象、动作和必要目的。例如“点击页面顶部的搜索按钮，展开关键词输入区域”。不收集详细推理文本，也不解析聊天中的自由段落作为执行事实。

## 5. 运行时如何记录

### 5.1 浏览器交互

当前页面观察完成、已经找到搜索按钮后，模型调用：

```json
{
  "description": "点击页面顶部的搜索按钮，展开关键词输入区域",
  "tool_name": "mcp__playwright__browser_click",
  "arguments": {
    "element": "页面顶部的搜索按钮",
    "ref": "e12"
  }
}
```

这是拟议的 `test_execute_operation` 参数。随后输入关键词时再次提交一条说明，使用原生 `browser_type` 参数。`ref` 保留在技术执行依据中，手工步骤主要显示页面位置、控件名称和实际输入。

执行顺序：

1. 程序确认已进入执行阶段，当前步骤存在且允许该工具；规划、未批准和停止后的业务动作仍被原有守卫拒绝。
2. 固定当前 `Binding`，生成操作 ID，保存说明与操作提案；模型不能指定实例、序号、成功状态或断言实际值。
3. 生成原生子调用 ID，建立操作与子调用的关系，持久保存后才调用原工具。
4. 子调用经过原有目标限制、审批、工具参数校验、取消和超时机制。封装只转交一次，不自行重试。
5. 依据原生派发与结果事件结算记录。模型需要调整或重试时，产生新的记录。
6. 原工具结果回到当前模型循环。文本、图片、错误状态及 SDK 上下文/终止标记按原生协议转交，不能把图片改成大段 JSON 文本，或把子调用错误包装成成功。

原有截图、录像与可信断言链路继续使用。首版不为每个操作新增一次截图或网页查询；关联本步已有证据和原生调用结果，不能把本步最后的截图冒充每个动作的独立截图。

```mermaid
flowchart LR
  A[观察当前页面] --> B[说明当前实际动作]
  B --> C[保存说明与固定归属]
  C --> D[同一 Agent 转交原工具]
  D --> E[原生审批与执行]
  E --> F[保存调用结果]
  F --> A
  F --> G[最终报告与手工用例]
```

### 5.2 哪些内容进入主要实际步骤

| 内容 | 建议处理 |
| --- | --- |
| 访问页面、点击、输入、按键、选择、拖动、必要的业务等待 | 通过带说明入口执行，进入主要步骤 |
| 页面快照、查找 DOM、查看可用工具等分析辅助调用 | 保留原生调用记录，默认不变成手工步骤 |
| 为用户检查点进行可信采集 | 关联本步采集说明和证据，正式“核对”行来自已有断言 |
| `test_current`、定义步骤、绑定检查、结束步骤等控制调用 | 不生成手工操作行 |
| 用户明确要求的准备或业务清理 | 在独立“前置条件／收尾”区域展示 |
| 插件自动浏览器复位、关闭及媒体收尾 | 保留执行记录，不混入用户业务步骤编号 |

支持的业务交互裸调原工具时，建议在执行前提示模型改用带说明入口；原生观察及插件内部采集继续走既有入口。校验须识别受信的内部子调用，不能误拦 `test_capture` 的 DOM、截图和关闭操作。

用户明确规定的准备与清理也可以保存说明，但入口和子工具必须仍符合当前冻结阶段的限制。清理守卫只放行原规则允许的转交，不能因为新增封装而允许恢复业务操作、扩展目标或跳过必要关闭。

这项约束只作用于发起测试的 Agent，结束后随已有测试作用域撤销，普通聊天和其他会话不增加相关工具或提示。

### 5.3 原子操作与复合操作

点击与输入分别记录。`browser_type` 的 `submit:true` 同时输入并按 Enter；为了得到两条可核对记录，首版建议让模型分别调用输入与按键工具。多字段填表同样优先逐字段执行，避免一批填写失败后错误地把所有字段标成完成。

任意 `browser_evaluate`／`browser_run_code` 脚本内部可能包含条件、循环或多个动作，普通工具结果不能证明每个子动作都成功。首版保守保存一条明确标注的“复合操作”，并把实际步骤完整性标为需复核；不能依据模型提供的若干小步骤直接宣布逐条执行完成。常规观察脚本继续属于辅助记录。

这意味着首版保证常规可分解交互的逐条记录，不承诺把任意脚本自动拆成可验证的原子手工步骤。实施时需在真实页面用例中验证模型遵循该调用方式的效果和耗时。

### 5.4 API 与检查行

API 请求仍由 `test_capture` 驱动，不能通过新入口直接调用内部 `test_api_get` 绕过可信采集。每次实际 HTTP 子调用根据本次采集原因、冻结定义和真实 URL 登记说明，例如“向查询接口发送 GET 请求；参数：keyword=agent”。多个真实请求分别记录，父采集调用与子请求不重复算两步。

断言行由程序从 `assertion_evaluated` 及 `AssertionResult` 生成，例如“核对响应状态码为 200”或“核对帖子正文不为空”。预期、比较器、实际值与证据沿用原记录，模型不再补交一套实际值或预期。

操作说明描述的目的不自动变成新增断言。点击后是否必须展开面板等中间预期，原任务没有规定时，手工用例的预期列标明待补充。

## 6. 数据怎么保存，编号怎么生成

建议在 `StepResult` 增加可选 `actual_operations`，使用单独的 `ActualOperation` 类型；仍由现有 `SuiteRun` 快照保存。字段职责如下：

| 字段 | 来源与用途 |
| --- | --- |
| `operation_id`、`order_in_step` | 程序生成的身份和本规划步骤内登记顺序 |
| `binding` | 从当前执行上下文固定运行、实例、阶段、规划步骤与尝试身份 |
| `description`、`description_source` | 简短说明；来源区分模型、采集原因、程序模板或缺失 |
| `parent_call_id`、`tool_call_id` | 关联封装／采集入口及真正的原生子调用；避免重复计数 |
| `granularity` | 可分解操作或内部明细未确认的复合操作 |
| `dispatch_observed`、`state` | 派发与结算事实，不能由模型声明 |
| `created_at`、`dispatched_at`、`finished_at` | 登记、进入派发通道和结算时间；调用耗时可引用原记录 |
| `reason` | 拒绝、错误、取消或未确认原因 |

实参、原始结果、观察和证据复用已有调用与采集记录，不复制一套不可同步的大对象。说明中的输入不作为数据依据；报告与导出显示原生实参投影出的实际输入，遵循既有脱敏规则。

新增 `operation_registered`、`operation_linked`、`operation_dispatched`、`operation_finished` 事件。继续使用现有 `state_saved` 快照进行重建；对同一调用的重复通知按操作 ID／调用 ID 去重。

最终显示顺序由程序遍历实例的业务 `StepResult`：先列该步实际派发的操作，再在原断言出现的位置插入检查行，生成 **1、2、3……**。每个数据实例从 1 重新开始，跨规划步骤连续编号。每行保留来源规划步骤，内部稳定 ID 不随显示编号改变。

未派发的操作提案进入“未执行的说明”附录，不占主要实际步骤序号；未来未执行的规划步骤不被补成实际操作。准备与清理另列。CSV 不同数据行即使操作相似，也不跨实例合并。

## 7. 失败、重试、取消与完整性

| 情况 | 操作记录与导出行为 |
| --- | --- |
| 原生调用成功结算 | 标注工具执行成功；业务是否通过仍看断言与清理 |
| 准入拒绝或取消，未观察到派发 | `NOT_DISPATCHED`，说明留在附录，不当作已执行步骤 |
| 已进入派发通道但返回错误 | 保存 `ERROR` 和实际依据；不能认定页面一定没有变化 |
| 在途结果无法确认、超时或进程中断 | `UNKNOWN`，完整性为不完整；重建不补造结果 |
| 模型调整定位并重试 | 新建记录，旧错误保留；不按相同文字自动去重 |
| 测试取消 | 保存取消前的真实操作和状态；未执行后续步骤不进入主要列表 |
| 冻结后收到迟到结果 | 只记录审计，不把封存未知结果改成完成，也不重排导出 |

进入 `tools/execute` 只证明进入原生派发通道，不等同于页面动作已经发生；现有 `CallRecord.body_started` 可能仍是 `unknown`。不能通过工具名称或某个 hook 推断外部副作用已经确认。

建议单独记录说明完整性 `COMPLETE／PARTIAL／NOT_RECORDED`，与 PASS、FAIL、ERROR 等业务状态区分。旧版本运行没有说明记录时标为未记录，继续展示原报告，不让模型事后补齐，也不把旧调用翻译后冒充运行时分析。

必需的操作记录写入失败时，沿用账本失败机制停止新的派发。派生的 Markdown／JSON 导出失败时，保留可重建的数据并提示重新生成；导出失败不改写既有断言。程序可以检查身份、关联、顺序和结构，不能证明任意自然语言说明都准确表达了页面语义，执行依据仍需可查看。

## 8. 报告与手工用例文件

### 报告

每个用例增加“实际步骤”选项卡。有新增记录时默认显示它；原“步骤”、断言、附件和录像仍可查看。主要行显示序号、简短说明、实际输入、状态及来源规划步骤，调用依据按需展开。长文字换行，多步骤在现有详情区域滚动，不在每行堆放原始 JSON。

切换实例时，只显示该实例的实际步骤，处理无此选项卡的旧数据回退；既有视频暂停与 API 无媒体规则继续生效。输入框上方的实时进度仍按规划步骤统计，本次不把其分母替换成实际操作数量。

### 保存与下载

建议每次运行生成：

```text
run-…/
  plan.json
  results.json
  events.jsonl
  actual-steps.json
  manual-cases.md
  report.html
  evidence/
```

`actual-steps.json` 使用独立的记录格式标识，按实例保存原任务、参数快照、规划映射、有序操作／检查、完整性和调用引用。它方便后续读取与转换，不能直接冒充冻结执行计划。

`manual-cases.md` 按实例生成用例名称、原始任务、已定义的前置条件、测试数据、有序操作与预期、收尾说明及本次状态。默认保留失败／重试和未知信息，明确标注需复核；首版不自动删除“看起来多余”的动作、生成理想路径或承诺该路径已重新复跑。

示例正文：

| 序号 | 操作步骤 | 输入 | 预期结果 | 本次记录 |
| --- | --- | --- | --- | --- |
| 1 | 点击页面顶部的搜索按钮，展开输入区域 | — | 待补充，原任务未定义独立检查 | 工具执行成功 |
| 2 | 在搜索输入框中输入本次关键词 | agent | 待补充，原任务未定义独立检查 | 工具执行成功 |
| 3 | 提交搜索 | Enter | 待补充，原任务未定义独立检查 | 工具执行成功 |
| 4 | 打开搜索结果中的第一条帖子 | 本次第一条结果 | 待补充，原任务未定义独立检查 | 工具执行成功 |
| 5 | 核对帖子正文不为空 | — | 正文不为空，来自原检查点 | 按可信观察显示 PASS／FAIL |

这个示例仅展示结构。真实文件只收录本次有记录的操作，输入与检查使用实际保存值。没有检查的行不补写“已验证”的中间预期；人可以补充手工检查，但不回写改变原运行。

报告提供“下载实际步骤 JSON”和“下载手工用例 Markdown”，同时保存完整批次文件；当前实例可复用已有内嵌文本下载方式。在线文件访问扩展现有认证白名单和 Markdown MIME，不增加写接口或绕过认证。Markdown 转义换行、竖线及特殊字符，所有持久化内容复用 `Recorder.sanitize`，敏感值和短期定位引用不成为手工执行依赖。

重建生成 `actual-steps-rebuilt.json`、`manual-cases-rebuilt.md` 和既有重建报告，使用保存事实，不覆盖原文件。步骤内容、顺序和绑定应与原文件一致；重建时间元数据可以不同。没有原始说明的旧运行不会生成一套声称完整的手工步骤。

## 10. 验收标准

### 自动回归

1. “搜索 agent”经两次真实交互保存两条说明、两个原生子调用及正确顺序；操作文本不把宏观规划重复当成实际动作。
2. 相同描述的不同调用不误合并；重复事件只登记一次；子调用晚到仍属于创建时的实例与规划步骤。
3. 规划／未批准／取消后的业务操作被拒绝；裸调受控交互得到模型提示，内部采集不被误拦；审批和取消保持原生管线。
4. 父封装与原生子调用不重复算两步；API 一次请求不因采集及多个断言重复计数。
5. 失败、重试、复合调用、拒绝、未结算、写入失败和迟到结果均按状态保存，不伪造执行成功。
6. 编号按实例业务顺序连续，准备清理分开；实际输入来自调用数据，预期来自冻结检查，解释不新增断言。
7. 新旧报告、CSV 多实例、长文字、特殊字符、脱敏、原／重建导出以及离线下载验证通过；API 无浏览器媒体。

### 真实公开 DSH 验收

在独立 profile 使用公开 npm DSH 和专用 Playwright MCP；用户当前服务保持原状。

- 使用初始隐藏搜索框的页面，验证“点击搜索按钮 → 输入 agent → 按 Enter”等操作分别登记；切换为初始就有输入框的页面，实际步骤不编造点击。
- 本机夹具验证定位失败后调整重试、拒绝／取消以及中途停止；核对报告、账本、真实页面与导出的动作数量、顺序、状态一致。
- 实际网站搜索用例验证文字规划、运行时分析与最终真实步骤的对应；真实界面细节以当次运行为准。
- 纯 GET JSON 及浏览器/API 混合批次验证实际请求／检查与实例隔离；两行 CSV 不混参数或说明。
- 验证原生文字、图片、错误和必要审批未被封装破坏；核对录制、正常清理、四个命令及旧报告回归。
- 从保存的 Markdown 按步骤人工走一遍，记录可理解性和缺失预期；这是手工可用性验收，不称作自动无模型回放。
- 对比原生交互次数与带说明入口的模型轮次、工具层调用及总耗时，明确增加说明和拆开复合动作的成本，不延长原执行预算。

## 11. 建议审核确认的取舍

| 取舍 | 本方案推荐 | 影响 |
| --- | --- | --- |
| 如何获得真实操作说明 | 同次带说明并转交原工具 | 关联可靠；新增一个内部工具，原生交互调用方式需要模型配合 |
| 记录粒度 | 常规交互逐条，无法核对内部明细的脚本保留复合标记 | 能还原搜索按钮与输入框操作，不能承诺任意脚本的原子展开 |
| 失败和重试 | 保留完整事实与状态 | 用户可复核和编辑手工用例，首版不自动筛成理想路径 |
| 预期结果 | 只引用既有检查，缺失标待补充 | 不改变测试判定；手工稿可能需要补充中间步骤预期 |
| 展示和文件 | 报告实际步骤默认页，JSON + Markdown | 便于查看与保存，不增加配置、用户确认弹窗或斜杠命令 |

确认方案后再进行代码实施。本轮未修改运行代码、构建产物或发布版本，未执行上述新增功能验收。
