# 收尾约束与账本报告优化实施方案

编写日期：2026-10-06。核对基线：包版本 0.10.0、GitLab 复杂用例交付提交 `08a331a`。

**状态：待审核，尚未实施。** 本文说明拟议修改；当前实现事实及原始失败见[GitLab 复杂用例验收](../project/GitLab复杂用例验收.md)。本次仅交付方案，不修改执行代码、依赖、版本或标签。

## 1. 要解决的问题

本次解决两件事：测试失败后可靠完成预授权收尾；复杂用例运行时减少重复存储，让日志、报告及重建可以处理大文件。

成功与否仍由冻结预期、可信采集和程序断言决定。失败、重试、超时、未结算调用及资源隔离记录必须保留。用例中的明确收尾说明可以继续使用，但插件的默认行为也要具备相同的执行约束。

### 1.1 已复现的运行问题

| 问题 | 实际证据 | 当前状态 |
| --- | --- | --- |
| 失败后的默认收尾仍允许业务操作 | 首轮 UI 的正文断言失败后，进入 `__close`，Agent 继续尝试编辑正文和执行页面脚本，随后收尾超时、环境隔离 | 后续样例用明确收尾指令规避；核心执行约束尚未修复 |
| 日志与报告体积异常增长 | 17 场景约 18 分钟的混合运行：事件日志 1,539,078,024 字节，HTML 323,793,166 字节；整文件读取日志的验收脚本触发 `Invalid string length` | 验收脚本已改流式读取；插件记录、生成及重建代码尚未优化 |

记录规模基线来自运行 `run-2026-10-06T01-06-14-286Z-c8bf4a9e`。初次收尾失败来自 `run-2026-10-06T00-55-51-094Z-a16e1966`。原件保持本地，不提交报告、账号、截图、录像或事件日志。

### 1.2 源码复核与体积归因

| 位置 | 已确认的实现 | 影响 |
| --- | --- | --- |

## 2. 范围与方案选择

| 选择 | 好处 | 代价 | 本次建议 |
| --- | --- | --- | --- |
| 仅加强收尾提示，压缩已有日志 | 改动少 | 不能阻止错误业务操作；完整快照仍重复保存；内嵌压缩日志仍扩大 HTML | 不采用 |
| 执行层限制自动释放，精简快照记录，独立日志下载与流式重建 | 能处理已复现问题，复用当前 Agent、报告和设置页 | 需调整账本内部版本及大文件处理；日志附件需随运行目录保存 | **采用** |
| 引入独立调度服务、数据库和新的报告应用 | 扩展空间较大 | 超出当前需求，增加部署、维护与迁移成本 | 后续有实际需求时再评估 |

本次不新增斜杠命令、常驻告警、服务、数据库或用户配置项；保持现有四个命令和设置页恢复入口。不扩大到多对话并行、API 写方法、App 自动化或模型执行策略重构。

## 3. 收尾与初始化的执行约束

### 3.1 根据当前步骤确定准入规则

在 NativeTest 内复用统一的准入判断，同时覆盖正常收尾和停止后的收尾。由程序根据当前 Entry 的来源、阶段与冻结采集定义判断自动资源释放；不能由模型提交字段来切换模式。

| 当前情境 | 允许的行为 | 约束 |
| --- | --- | --- |
| 普通业务步骤 | 当前冻结范围内的观察、带说明操作、可信采集与结算 | 继续使用现有目标、审批和串行限制 |
| 插件生成的 `__reset` / `__close` | `test_current`、`test_capture({})`、`test_finish_step`、`test_fail_step`，及结算完成后的 `test_finish` | 仅放行由可信采集入口派发的 browser_close 子调用 |
| 用户声明、仅采集 browser_close 的清理步骤 | 同上 | 采用相同释放规则，防止换一个步骤 ID 就绕过限制 |
| 用户声明的业务清理 | 当前冻结清理步骤授权的操作和采集 | 保留原有清理能力；不能重新定义步骤、修改旧检查或返回业务执行 |
| 停止等待在途调用结算 | 已派发调用的结果结算 | 禁止新业务动作，结算完成后才开始清理 |

纯释放步骤拒绝：点击、输入、导航、页面快照、任意 `browser_evaluate` / `browser_run_code`、操作封装以及 shell/API 绕行。关闭必须来自插件实际生成并登记的可信子调用；仅带一个 parent 字段不足以放行。

复用现有 `cleanupAllowed()` 的约束，但不能直接把它应用于 `__reset`：现有实现主要检查 cleanup 阶段，初始化是 setup。实施时将纯释放判断独立出来，供 setup、正常 cleanup、停止 cleanup 共用；只增加这一必要判断，不另建状态机。

守卫与 `test_execute_operation` 入口都检查当前范围。守卫负责阻止原生派发，入口负责防止操作登记或内部转交误把关闭阶段当作浏览器业务。可信关闭调用继续走同一 Agent 的原生管线及原有审批策略。

### 3.2 让模型和用户知道当前在做什么

`test_current` 的 next 及当前动态指导按阶段返回明确动作。例如：

> 当前进入浏览器释放阶段。调用 test_capture({})，取得释放证据后调用 test_finish_step。已完成检查保持冻结，随后按 test_current 进入下一实例或生成报告。

误调工具返回具体原因和正确下一步，例如“当前只允许释放浏览器，请调用 test_capture({})”。该拒绝进入现有脱敏调用记录，不生成成功的实际业务步骤。

进度区沿用已有 cleanup 状态，显示正在收尾及耗时。提示只出现在本次测试或设置页；安装插件但没有使用测试功能的用户不显示常驻提醒。

### 3.3 成功、失败和隔离规则

1. 业务断言 FAIL 后保留原断言，阻塞本实例尚未执行的依赖步骤，按冻结计划收尾。
2. 关闭已通过可信采集确认、调用已结算且媒体已完成收尾后，按现有规则释放资源并继续下一实例。前一实例仍显示真实失败。
3. 收尾失败、超时或在途操作无法确认时，继续隔离并保留处置原因。被拒绝的工具不会执行；如果模型一直没有完成正确关闭，仍按真实超时处理，不能自动认定资源已释放。
4. 不扩大 cleanupTimeoutMs，不无限重试，不删 quarantine.json 绕过恢复。恢复继续使用“设置 → 测试插件 → 释放环境”的原生关闭与证据流程。
5. 纯接口实例不创建浏览器初始化、关闭、画面浮窗或录像记录。

## 4. 账本保存与大文件重建

### 4.1 保留事件，去掉重复全量状态

保留现有工具绑定、派发、结果、断言、实际操作、修订、录像与停止事件；保留写失败立即停止派发的规则。`state_saved` 的完整运行对象不再随每次保存追加到新账本。

推荐保存结构：

```text
run-.../
  plan.json
  events.jsonl                 # 业务事件及简短快照提交记录
  results.json                 # 最新完整状态，供现有界面和索引读取
  checkpoints/
    state-<序号>.json          # 最近已提交快照
    state-<上一序号>.json      # 上一份已提交快照
  evidence/                   # 原有响应、图片、录像
  report.html
  actual-steps.json
  manual-cases.md
```

快照提交记录包含相对路径、覆盖的事件序号、字节数和 SHA-256，不再复制 SuiteRun。仅保留最近两份已提交快照及写入中的临时文件；不能把每次完整状态改存成永久新文件，导致只是转移磁盘膨胀位置。

初步写入顺序：

1. 已发生的业务事件按现有持久化约束写入；计算本次快照所覆盖的事件序号。
2. 对完整状态脱敏，写临时快照，fsync 后原子重命名。
3. 追加快照提交事件并 fsync，使这份快照成为可验证的重建起点。
4. 原子更新 results.json；全部必要写入成功后返回，再允许依赖此次保存的工具派发。
5. 清理更早的快照，只清理程序确认归属的检查点文件。业务事件和原始证据不删除；清理失败保留文件并提示本次运行，不冒充业务失败或破坏已提交快照。

第一次提交必须包含完整起点。若进程在步骤 2 和 3 之间退出，未提交文件不被当成权威状态；若在步骤 3 和 4 之间退出，可由已提交快照重建。没有可验证起点、记录中间损坏或已提交快照哈希异常时，报告必须明确完整性错误；不能静默回退并把旧状态称为当前结果。

本阶段保留现有必要保存频率及 fsync。异步缓冲、按时间减少保存或放宽派发前持久化均不在首版范围内，以免丢失实际操作和取消证据。高频原子写的成本单独测量后再决定是否需要下一轮优化。

### 4.2 新旧账本的读取

新的账本版本与 SuiteRun / 可执行计划格式分别管理；增加新快照提交事件，不复用旧 `state_saved` 的字段语义。SuiteRun 和现有计划输入格式保持兼容。

- 新账本使用外部快照引用；旧账本仍识别原有内嵌 `state_saved`。不批量改写历史记录。
- 快照路径沿用 safePath、符号链接约束、600 文件权限和已有敏感值脱敏；每份已使用的快照验证字节数、哈希、运行 ID 与事件位置。
- 先确定最后两份已提交引用，再校验应保留的文件；更早引用按明确保留策略淘汰，其事件仍保留，不能因为这些文件已正常回收而报损坏。最新应保留文件缺失或损坏则报完整性错误。
- 旧事件已经很大也要能逐行处理；不能仅修新文件读取。
- 新旧重建都保留序号连续性、修订及应用记录、待结算调用、UNKNOWN 状态与资源隔离检查。重建只读事实，不发请求、不调用模型、不重新执行动作。
- 最新快照之后的运行状态事件须补入其已经落盘的事实，或明确标为未封存和中断；不能静默忽略后续步骤结果或断言，然后返回完整状态。没有确认的工具结果继续 UNKNOWN。

### 4.3 流式处理与中断

把 rebuild 改为异步逐行读取，通过有限状态保存序号、在途调用、修订记录及待处理的操作事件，不把完整日志或全部行放进数组。已有快照覆盖的操作历史不用继续累积在内存中。如需要先定位最后提交点，再读取其后的操作事件，可采用两次顺序扫描，避免引入索引服务。

调用方 TestUiAccess 改为 await，并传递现有请求取消信号；同步修改 scripts/validate-report.mjs 和全部相关测试调用方。取消读取时关闭文件流，保留原件和已完成的独立文件；临时重建产物不发布为成功。尾部截断可以标为中断，中间损坏或序号断裂拒绝可信重建。

单个旧 `state_saved` 行仍需要解析其完整 JSON；内存目标是“单行、最新状态及必要索引规模”，不能承诺任何大小的单条 JSON 都可无限处理。异常必须可解释，不能默默忽略。

## 5. 报告生成与下载

### 5.1 首先移除最大重复来源

1. 从 HTML 删除 `gzipSync(readFileSync(events.jsonl))` 和日志的 Base64 数据。
2. 事件日志下载链接指向同目录 events.jsonl。如保留“下载压缩账本”，用 Node 流式 gzip 写成 events.jsonl.gz，只生成一份，不再内嵌。报告先完成主要文件；可选压缩失败时保留未压缩下载并说明，不能因此改变断言或释放状态。
3. 同一下载内容建立单一数据索引，各显示区域引用同一份内容。小型 JSON / Markdown 的离线下载仍可由浏览器从唯一数据生成 Blob，避免把相同 Base64 链接重复放进多个区域。
4. 原生调用详情按 call_id 保存一次；实际步骤、规划步骤均引用该详情，展开时创建相应视图。通过 textContent 等安全文本接口呈现，不把工具输出作为 HTML 执行。收起区域只按需创建详情 DOM，单纯增加折叠不能减少文件体积。
5. 截图先保留现有内嵌展示，单个证据需要同时预览和下载时共用同一数据；视频保持相对路径、按实例归属与既有 Range 支持。

报告继续直接展示原始任务、规划、实际步骤序号、输入、预期、真实结果、失败及证据；不通过裁掉失败工具输出或删掉断言操作数来达到体积目标。

### 5.2 在线认证与离线边界

独立日志不能直接照搬相对链接后就算完成：当前报告运行在 opaque sandbox 内，严格 Cookie 可能不随附件请求发送；MP4 已通过文件专用只读票据处理这一情况。

本次复用该机制，扩展到**报告实际链接的日志附件**：

- 票据仍由已认证的 HTML 响应签发，绑定准确的运行 ID、文件路径和到期时间；仅允许一个文件的 GET/HEAD。
- 只准入 events.jsonl 及存在的 events.jsonl.gz，不因扩展票据允许任意目录、所有 JSON、写请求或其他运行文件。
- 离线磁盘 HTML 只保存相对路径；签名在 HTTP 响应中注入，不能写入离线原件。
- 大型日志和附件用 createReadStream 发送，并响应客户端断开；压缩与重建也及时关闭流。HTML 仍使用原有 sandbox 和 CSP，不增加外部网络源或 allow-same-origin。

**使用方式变化：** 单独复制 report.html 仍能查看结论、步骤、断言及保留的内嵌内容；下载独立账本和播放录像需要保留完整运行目录。既有录像已经依赖目录中的 MP4，此次文档需明确把日志也列入保存范围。

运行日志保留原文件名，重建报告及 JSON／Markdown 继续使用 -rebuilt 名称。重建不覆盖原报告、不改变原结果；压缩文件为可再生的附属产物，生成中不对下载开放。

## 7. 验收清单

### 7.1 执行正确性

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |

### 7.3 规模与报告体验

以下是**验收目标，不是已获得的优化结果**：

| 指标 | 目标与比较方式 |
| --- | --- |
| 同一旧运行生成的新 HTML | 不超过 30 MB，较 323,793,166 字节减少至少 90%；内容完整性先于体积达标 |
| 最终 17 场景新账本 | 对可比调用规模的基线，events.jsonl 目标不超过原体积的 10%；同时统计检查点和整个运行目录，防止把重复转移到其他文件 |
| 增长方式 | 使用固定大小响应、不同数量独立实例的确定性夹具，验证日志随事件数量近似线性；不会因每步重复历史快照持续放大 |
| 大文件能力 | 可读取本地 1.54 GB 旧日志；常规回归使用较小分块夹具验证跨块与尾损坏，1 GB 以上压力验收单独运行 |
| 报告生成与下载 | 日志压缩、下载、重建不整体加载日志；记录耗时、峰值内存及事件循环延迟，不能仅凭文件变小宣布性能通过 |
| 浏览器体验 | 本机首次可交互目标 3 秒内；切换实例、展开调用、下载及录像播放逐项验证，记录浏览器和宿主版本 |
| 混合 UI/API 报告 | UI 保留截图、录像、实际步骤；13 个 API 实例没有截图预览、录像区域或浏览器关闭占位 |

最终真实验收重新准备干净数据，完整运行修订后的 all.json。既有分轮通过不能代替此次整套回归。故意失败的收尾用例单独运行，明确预期为 FAIL 且关闭成功，不能为了“全绿”调整断言或抹除失败。

公开 SDK 验证包括 typecheck、build、单元/集成测试和 verify:package。测试总数以实施后的实际执行为准，不沿用旧的 268 通过数作为新版本证据。GitLab 账号继续从 Git 忽略的本地配置读取。

## 8. 风险、处理与交付边界

| 风险 | 本次处理 |
| --- | --- |
| 释放守卫误拦可信关闭或自定义清理 | 分别验证 setup、普通 cleanup、停止 cleanup、同一 Agent 的真实父子调用和自定义清理，不仅测试提示文字 |
| 快照格式变更影响历史重建 | 保留旧版本读取器及流式回归；不迁移原件；未知版本明确拒绝 |
| 删除历史快照影响审计 | 原始业务事件和证据持续保留；仅清理保留策略管理的全量状态副本，保留最近两份已提交起点；不承诺保留每个历史时刻的完整快照文件 |
| 独立日志在 sandbox 中下载失败 | 文件专用短期只读票据与严格 Cookie 的真实浏览器验收；不降低宿主认证 |
| 为缩小体积丢失失败、脱敏或实际步骤 | 对新旧纯数据投影进行一致性比较，核对 FAIL/ERROR/BLOCKED、UNKNOWN、重试和手工导出 |
| 体积指标受模型重试或页面响应变化影响 | 保存固定夹具比较与真实运行两种证据；对调用数、响应字节量归一化后再判断 |
| 保留每次原子快照仍有写入成本 | 首阶段保证持久化与可恢复性；记录开销后再评估减少写入，未经新的故障验收不采用缓冲派发 |

本方案不把模型漏输入或定位失误全部转成插件自动修复。冻结预期与严格断言继续暴露这些失败；本次确保失败以后能够可靠收尾，以及完整保留并高效查看证据。

批准实施后，交付代码、回归测试、完整 GitLab 验收和更新后的使用/故障文档，再提交本地供审核。实际修复和性能目标全部验证后，才能记为完成。
