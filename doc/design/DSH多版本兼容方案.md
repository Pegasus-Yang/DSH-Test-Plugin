# DSH多版本兼容方案

[文档导航](../README.md) · [本轮兼容性核查](../project/DSH三个alpha版本兼容性核查.md) · [当前实现](../architecture/当前实现.md) · [版本发布](../deployment/版本发布与Git标签.md)

2026-10-17 方案，已获用户确认并按 0.13.0 实施。本文保留审核时的原始基线与拟议步骤；当前实现和交付结果见[0.13.0 验收](../project/0.13.0多版本兼容验收.md)。

原方案：目标是让后续**同一个发行包同时支持 DSH `0.2.1-alpha.1`、`0.2.1-alpha.2`、`0.2.1-alpha.3`**，并在以后升级开发 SDK 时保留已经支持的宿主。

当前插件 `0.12.3` 的 22 个 DSH peer 都精确限定 `0.2.1-alpha.3`。alpha.1、alpha.2 会被宿主兼容检查跳过；这与接口是否实际可用是两个判断。本轮保持正式代码、依赖、`dist` 和支持声明原样，先以同一个发行包核查三个版本，结果和实验条件见[核查记录](../project/DSH三个alpha版本兼容性核查.md)。

核查中三版各 363 项回归及 9 轮真实 Markdown 核心场景通过，旧宿主的原包运行使用临时精确豁免。本轮覆盖链路未发现需要新增版本分支的 API 差异；首次实施重点是统一准入声明和验证门禁，再完成正式无豁免发行验收。

## 一 支持范围与维护规则

### 首次支持集合

| DSH 宿主                              | 本方案的交付目标                 | 当前发行包的正常加载声明                                   |
| ------------------------------------- | -------------------------------- | ---------------------------------------------------------- |
| `0.2.1-alpha.1`                       | 支持；纳入必跑矩阵               | `0.12.3` 不允许；历史 `0.12.1` 声明此版本                  |
| `0.2.1-alpha.2`                       | 支持；纳入必跑矩阵               | 当前核对的 `0.12.1`、`0.12.2`、`0.12.3` 标签均未声明此版本 |
| `0.2.1-alpha.3`                       | 支持；继续作为开发和发行构建基线 | `0.12.3` 已声明                                            |
| 其他 alpha、rc、正式版及 `0.2.0` 系列 | 尚未纳入；增加基线后再决定       | 不因版本号接近而自动宣称支持                               |

范围沿用当前插件的 Node.js `22.19+`、DSH Web、native 工具模式与单批并发 1。多版本兼容不改变当前 Agent 执行、原生审核、可信采集、停止收尾、资源隔离和报告规则，也不增加同时执行多个测试的能力。本轮本机核查平台为 macOS arm64、Node.js `22.22.3`；发行 CI 继续使用既有 Linux 环境，增加三个宿主版本维度。

后续常规插件版本继续继承这三个宿主的支持集合。更新 `devDependencies` 只改变构建基线；只有实际接口或行为使旧宿主无法继续支持，并完成对应取舍审核后，才提高支持下限。

DSH 仍处于预发布阶段，首次采用明确版本集合。建议的 peer 值为：

```text
0.2.1-alpha.1 || 0.2.1-alpha.2 || 0.2.1-alpha.3
```

这是一份包支持三个宿主，不是给三个宿主各维护一套发行包。它也不会把未验证的 alpha.4、rc 或正式版一并放行。另一种做法是声明较宽的未来版本范围，减少以后扩展声明的频率；代价是新预发布版可能在未经验证时直接加载。首次交付建议选择明确集合，待上游接口稳定后再评估扩大范围。

### 升级宿主时的判断

1. 所用接口和行为未变：保留旧支持集合，增加新基线；不增加运行时兼容代码。
2. 差异局部且可以保持语义：在相应接入点做小范围适配，旧、新路径都进入矩阵。
3. 核心语义无法同时维持：说明受影响功能和原因，再建立新支持系列，保留旧宿主最后可用的插件标签。

不能通过删除 peer、改为 `*`、打包第二份宿主 SDK，或默认要求用户授予版本豁免来实现正式支持。

核对基线为官方发布标签，不混用本机其他源码提交：

当前没有据此引入统一宿主适配类的必要。实施时若某项实测发现真实 API 差异，将差异放在所属接入模块；只有多个模块需要复用同一转换时才提取小型兼容文件。必需审核、可信采集、停止和资源释放能力缺失时明确拒绝该功能，不能静默跳过后生成 PASS。

## 四 必要改造与文件范围

### 单一兼容策略

建议新增仓库级 `dsh-compatibility.json`，作为开发和发布检查的数据来源：

```json
{
  "buildSdk": "0.2.1-alpha.3",
  "supportedHosts": ["0.2.1-alpha.1", "0.2.1-alpha.2", "0.2.1-alpha.3"]
}
```

这是维护配置，用户无需填写。文件名刻意区分于 DSH profile 内用于授予风险豁免的 `compatibility.json`，两者不能互换。

`supportedHosts` 生成 peer 联合范围和 CI 宿主列表；`buildSdk` 核对开发依赖。保留 `package.json` 的正式声明，增加检查阻止两处漂移。生成或同步必须由维护命令显式执行，构建过程中不静默修改清单和锁文件。

这三个宿主基线按 DSH peer 做准入检查，不能只新增 `engines.dsh` 来放宽支持。以后使用新宿主提供的该字段时，应从同一策略生成，并继续保留旧宿主可读的 peer 声明。

### 最小文件清单

| 文件                                                           | 需要的改造                                                                                                                     |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `package.json`                                                 | 22 个 DSH peer 使用同一支持集合；保留 optional 属性；开发 SDK 仍固定 alpha.3；增加兼容检查命令，发行文件包含策略清单供解包核对 |
| `dsh-compatibility.json`                                       | 保存构建基线和三个必测宿主                                                                                                     |
| `scripts/check-package.mjs`及必要的兼容检查辅助脚本            | 检查政策、peer、开发依赖、候选包清单和版本一致；支持输出 CI 矩阵数据                                                           |
| 新的矩阵驱动与夹具                                             | 一次构建后，将同一 tgz 安装到各独立宿主；验证加载、业务、报告、空闲和处置证据                                                  |
| `.github/workflows/ci.yml`                                     | 保留既有发行构建检查，增加三个宿主作业，汇总门禁和失败证据                                                                     |
| `pnpm-lock.yaml`、`pnpm-workspace.yaml`                        | 仅在清单变更确实影响锁文件时更新；不因支持旧宿主而整体降级开发 SDK                                                             |
| README 中英文、安装与运维中英文、当前架构、文档导航、changelog | 分开说明开发基线、支持集合、已验证范围和旧宿主安装方式                                                                         |

生产模块和 `dist` 仅随确有必要的运行时调整或正式发行重建而变化。本轮核查脚本保存在忽略目录；实施时再将经过整理的矩阵驱动纳入仓库。矩阵证据记录宿主、SDK、基础依赖、Node、插件版本和产物摘要，沿用现有业务报告格式。

## 五 多版本验证与发布门禁

### 一次构建和独立宿主

1. 在无宿主源码链接的干净副本，用当前冻结锁文件完成类型、构建、`dist` 一致性、入口导入和现有回归。
2. 生成一次候选 tgz，记录 SHA-256。所有宿主消费同一个文件，不按宿主重建插件，也不回写包版本。
3. 每个宿主使用独立安装目录、`DSH_HOME`、profile、工作区、输出、MCP 和浏览器上下文；不读取或改写开发者正在运行的服务。
4. 核对实际传递 SDK 属于目标版本；Cordis、Schemastery 等基础包按对应宿主发行基线准备。profile 不安装另一套 DSH SDK，不能靠 `link:host` 补包。
5. 输出安装锁文件、SDK 来源、发行包摘要、运行记录与停止证明；所有作业成功才通过汇总门禁。缺浏览器、标签、宿主或用例时失败，不以 skip 代替验收。

应分别验证两种安装条件：一是对应发行基线的纯 SDK 组合，用于判断 API 兼容性；二是用户实际使用的公开安装路径，用于判断该宿主发布包能否正常安装。前者允许用同批版本约束隔离依赖漂移；后者必须保留公开依赖解析事实。不能将修正过依赖图的结果写成普通安装已经通过。

### 每个宿主的必测内容

| 层次       | 验证内容                                                               | 成功标准                                                                   |
| ---------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 安装与准入 | 候选 tgz 安装、启用、停用、卸载和重启；发布后固定 Git 标签复核         | 无豁免即可加载，清单和包版本正确；不留重复挂载或 SDK 副本                  |
| 静态与合同 | 针对目标公开 SDK 的类型检查；现有单元与集成回归                        | 类型检查通过，现有 363 项全部通过；将替身测试与真实宿主验证分开记录        |
| 原生审核   | Markdown 计划、关闭／要求修改、重新提交、批准、取消                    | 未批准无业务调用、无冻结计划；批准后只执行对应草案；关闭结果两种形状均正确 |
| 网页业务   | Markdown 用户入口、本地固定页面、真实 Playwright MCP、进度、证据和收尾 | 固定检查通过，原会话执行与清理，浏览器资源确认释放                         |
| 接口与反例 | Markdown GET JSON 正向、固定错误预期、CSV 多实例                       | 真值匹配时 PASS，不匹配时 FAIL；数据与实例互不污染，API 无浏览器媒体       |
| 停止与隔离 | 执行中停止、在途结算、未能确认结算、同会话清理、重启恢复               | 停止后无新业务；未知状态保持隔离，不能伪造释放                             |
| 设置与报告 | 可编辑 profile 中保存偏好和 MCP、重启回读；认证报告与导出              | 最终配置确已持久化；HTML、账本、手工导出和统计一致                         |
| 连续运行   | 本轮结束后在原会话及新会话启动下一轮；恢复普通聊天                     | Agent 已空闲，测试作用域和互斥已释放；无工具或提示污染                     |
| 安装边界   | 支持集合外的宿主、漂移的 peer、缺失的 SDK 与不完整包                   | 给出准确不兼容或缺包原因，不自动授权版本豁免                               |

完整 GitLab 回归继续从不提交的本机配置取账号，包含 Markdown UI 与接口入口，保留固定业务种子和本轮数据清理。本次本地夹具核查不能代替该项正式发布验收，也不能代替 RunBridge 实机、Browscreen 录像与不同操作系统的对应验证。

CI 的确定性合同和浏览器夹具适合每次变更运行；真实模型及私有 GitLab 验收使用受控配置，在首次扩展支持集合和正式交付前完成。真实模型不可用时只能记录该层未完成，不能用模型替身的结果顶替。

本地审核与候选门禁使用本地 tgz。用户手动推送版本提交和附注标签后，再复核固定 Git 标签安装及远端目标提交；这项发布后检查不能提前写成本地已经完成。

### 新宿主加入流程

新增版本先在验证列表之外做探测，审阅本项目触达接口的源码差异。确认安装、合同和行为后，再更新支持集合；已有三个宿主继续必测。未来若采用较宽的 semver 范围，也须分别记录“允许加载的范围”和“实际跑过的宿主”，并通过预览探测及时发现断裂。

## 六 旧宿主用户的使用方式

### 正式兼容版本交付前

| 用户宿主 | 当前可明确说明的方式                                                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| alpha.1  | 已在 `0.12.1` 上正常使用的用户保留此组合；该标签的 peer 为 alpha.1。需要回退时可固定 `github:Pegasus-Yang/DSH-Test-Plugin#v0.12.1`，同时遵循原版本的配置和功能范围 |
| alpha.2  | 保留原已验证可用的组合。当前核对的三个历史标签没有为 alpha.2 声明支持，不能把某个旧标签凭推测写成推荐版本                                                          |
| alpha.3  | 继续使用固定标签 `github:Pegasus-Yang/DSH-Test-Plugin#v0.12.3`                                                                                                     |

alpha.1 的旧版安装示例：

```sh
dsh plugin --profile web add github:Pegasus-Yang/DSH-Test-Plugin#v0.12.1
```

本轮给 alpha.1、alpha.2 的临时 profile 授予精确豁免，只用于验证原包的接口和行为。它没有改变当前发行包的支持声明，不作为默认安装或升级步骤。

### 正式兼容版本交付后

建议将首次多版本支持作为一个独立交付，拟使用 `0.13.0`；最终版本号由实施交付确认。本轮不创建该版本和标签。下列命令仅表示拟议交付后的用户入口，必须在版本提交和附注标签完成、用户审核并推送后才成为可用安装命令：

```sh
dsh plugin --profile web add github:Pegasus-Yang/DSH-Test-Plugin#v0.13.0
```

三个目标宿主使用同一地址、同一包、同一配置。升级后重启 DSH 并刷新浏览器，在插件页核对实际版本；支持集合内的用户无需为了插件升级而先升级 DSH，也无需选择专门的 alpha.1／alpha.2／alpha.3 插件变体。

如果以后确需停止支持旧宿主，安装指南必须列出“宿主版本 → 最后支持的插件标签 → 新版最低宿主 → 配置或数据迁移要求”。插件 `latest` 和 DSH `latest` 相互独立，旧宿主使用固定标签；发生拒绝时保留原配置和证据，再按对应表处理，不能默认安装 latest 一定匹配。

## 七 实施顺序与完成标准

| 阶段           | 工作                                                           | 通过条件                                                       |
| -------------- | -------------------------------------------------------------- | -------------------------------------------------------------- |
