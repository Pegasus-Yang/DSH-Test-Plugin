# 数据契约与状态规则

本文为拟议 v1 合同，是后续实现与测试的共同依据；不是已实现 Schema。M1 将这些约定实现为运行时校验和 TypeScript 类型。所有日期使用含时区的时间戳；耗时使用单调时钟测量，单位毫秒。

## 1. 身份与对象

| 对象 | 必备字段 | 不变约束 |
| --- | --- | --- |
| TestSuite | schema_version、suite_id、name、cases、source_refs | 导入后校验通过才执行 |
| TestCase | case_id、name、preconditions、datasets、steps、cleanup | case_id 在 suite 内唯一，至少一个必需业务断言 |
| DataRow | data_id、inputs、expected | data_id 在 case 内唯一；输入和预期完整绑定 |
| Step | step_id、kind、description、depends_on、required | kind 为 action/assertion；准备、业务、清理复用此结构；ID 在 case 内跨阶段唯一 |
| ActionSpec | goal、capability、allowed_targets、inputs、outputs、completion_requirements | outputs 声明输出名及值 Schema；必要输出必须列入 completion_requirements |
| AssertionSpec | observation_ref、operator、expected_ref/literal/expected_observation_ref、rule_ref | 三种预期来源恰选一种；引用与比较规则在执行前冻结 |
| SuiteRun | suite_run_id、plan_revision、manifest、instances、lifecycle | 一次提交对应一个批次；实例集合在开始前展开 |
| CaseRun | case_run_id、case_id、data_id、session_id、attempts、status、applied_revisions、effective_required_assertion_ids、resources | case/data 对应一条实例；保存实际生效版本、必需业务断言集合和资源身份 |
| ToolCallRecord | call_id、root_call_id、binding、name、args_redacted、times、outcome | 调用开始时冻结 binding；迟到结果仍归原步骤 |
| Observation | observation_id、producer、binding、context_id、output_name、value、evidence_refs、observed_at | producer 保存 call_id、adapter 版本及字段提取路径；禁止跨实例/上下文取值 |
| AssertionResult | assertion_id、binding、expected、actual、operator、status、evidence_refs、operand_snapshot、plan_revision | 保存实际使用的观察 ID、字段路径、值和生效版本；模型不能直接写 status |
| Evidence | evidence_id、relative_path、media_type、sha256、redacted | 指向已归档文件；路径不能逃逸批次目录 |
| PlanRevision | revision、parent_revision、reason、source_refs、added_steps、target_instance_ids、insertion_boundary、post_hoc | 追加修订；每个新增步骤显式 required；适用集合不可随重建变化 |

`binding` 包含 suite_run_id、case_run_id、phase、step_id、attempt_id，phase 为 setup/test/cleanup，由 runner 持有，模型只提交动作/观察需求。Agent session 与 case_run 的映射由插件创建；DSH 的 turn/step 只是诊断关联，不作为测试步骤主键。

`preconditions` 和 `cleanup` 都是 Step 数组，依次执行准备、业务、清理；依赖只指向本阶段或已执行阶段的前序步骤，不允许环和必需步骤依赖可选步骤。清理步骤另含 `run_if`（always 或 resource_exists）及 `resource_ref`；后者在 resource_exists 时必填。ActionSpec.inputs 使用 literal 或 input_ref/resource_ref 的显式绑定，不执行表达式。resources 由 runner 登记资源身份、所有权、创建状态和环境可信度；部分准备失败时也必须保留已经创建的资源。清理只可使用预先授权目标及本实例资源，不能根据模型猜测删除目标。

准备条件不满足记 BLOCKED；准备工具/协议异常记 ERROR。清理条件经可信记录确认不成立时记 SKIPPED 且注明不适用，不算清理失败；条件成立的必要清理必须完成，失败或缺少完成证据记 ERROR。资源创建状态必须区分存在、确认不存在、未知；缺少资源 ID 不证明未创建，未知且无法安全定位时记 ERROR 并隔离，不能当作不适用跳过。共享资源不可信时阻断依赖它的剩余实例；首版未声明独立资源的实例按依赖共享环境处理。清理完成条件必须验证实际重置/删除结果，不以提交成功代替；在途未结算时按下文隔离规则处理。

来源引用至少包括类型（用户用例/项目规则/Skill/诊断推断）、文件或 URI、版本/摘要、定位与摘录。首期项目知识不强制建设向量库，可使用已有只读检索 MCP 和显式文档。

## 2. 结构化用例示例

以下是合同示意，不是可直接交给已存在插件运行的文件。敏感值使用引用，不写明文密码。

```json
{
  "schema_version": "1",
  "suite_id": "login-check",
  "name": "登录验证",
  "source_refs": [{"id": "req-1", "kind": "user_case", "uri": "user:login-check", "version": "1", "locator": "原始输入", "excerpt": "使用有效和无效凭据验证登录结果"}],
  "cases": [{
    "case_id": "login",
    "name": "凭据校验",
    "preconditions": [
      {"step_id": "prepare", "kind": "action", "description": "验证测试账号配置并创建干净浏览器上下文", "depends_on": [], "required": true,
       "action": {"goal": "准备独立登录环境", "capability": "browser", "allowed_targets": ["fixture-login"], "inputs": {"credential": {"input_ref": "data.inputs.credential_ref"}}, "outputs": {"ready": {"type": "boolean", "const": true}}, "completion_requirements": ["ready"]}}
    ],
    "datasets": [
      {"data_id": "valid", "inputs": {"credential_ref": "fixture:valid"}, "expected": {"authenticated": true}},
      {"data_id": "invalid", "inputs": {"credential_ref": "fixture:invalid"}, "expected": {"authenticated": false}}
    ],
    "steps": [
      {"step_id": "submit", "kind": "action", "description": "提交当前数据行的凭据", "depends_on": [], "required": true,
       "action": {"goal": "完成一次登录请求并采集结果", "capability": "browser", "allowed_targets": ["fixture-login"], "inputs": {"credential": {"input_ref": "data.inputs.credential_ref"}, "context": {"resource_ref": "browser_context"}}, "outputs": {"auth_result": {"type": "object", "properties": {"authenticated": {"type": "boolean"}}, "required": ["authenticated"]}}, "completion_requirements": ["auth_result"]}},
      {"step_id": "check", "kind": "assertion", "description": "核对身份状态", "depends_on": ["submit"], "required": true,
       "assertion": {"observation_ref": "submit.auth_result.authenticated", "operator": "eq", "expected_ref": "data.expected.authenticated", "rule_ref": "req-1"}}
    ],
    "cleanup": [
      {"step_id": "release", "kind": "action", "description": "关闭并确认本实例浏览器上下文已释放", "depends_on": [], "required": true, "run_if": "resource_exists", "resource_ref": "browser_context",
       "action": {"goal": "释放本实例上下文", "capability": "browser", "allowed_targets": ["fixture-login"], "inputs": {"context": {"resource_ref": "browser_context"}}, "outputs": {"released": {"type": "boolean", "const": true}}, "completion_requirements": ["released"]}}

```

M1 需对必需字段、互斥字段、未知比较器、跨阶段重复 ID、循环/非法依赖、未绑定变量、非法证据路径及零必需业务断言做负向测试。示例中的能力名由配置映射到 M0 锁定的真实工具；准备 adapter 在创建上下文时向 runner 登记 browser_context，失败前已创建的资源也要登记。outputs 中的 Schema 由 adapter 的可信原始结果验证，不由模型宣称满足；示例不是已完成宿主验证的工具配置。

## 3. 数据展开与版本

每个 case 的每条 data row 生成一个 CaseRun；无参数用例显式生成一个 `default` 数据行。不同 case 只使用各自数据，不自动笛卡尔积。全批次实例数为各 case 数据行数之和。

先绑定每行输入/预期，再验证，最后固定实例列表；发现不完整数据时拒绝该计划执行并输出诊断，不静默丢行。用户明确要求只运行可用子集时，创建标明排除原因的新计划。

计划和知识版本在运行前固定。动态检查可新增 required=true 的必需业务断言，并影响适用实例结果，包括有明确来源的事后检查；必须保留 post_hoc 标记。新增步骤不得篡改既有步骤的预期、required 和结果，不能伪装成原始覆盖项。

PlanRevision 先校验来源、授权、依赖、输出引用和预算，再以单 writer 顺序提交。适用对象限 CREATED 或仍在 RUNNING 的实例；不接受已进入清理、CANCELLING、FINISHED 或 INTERRUPTED 的实例。运行中实例只能在无在途调用、观察写入完成的业务步骤边界应用，插入点必须尚未经过；不能满足则拒绝该修订，不静默缩减适用集合。当前实例可以使用已冻结的观察；需要新观察时必须显式追加只读采集动作。

写入 plan_revised 后，为每个适用实例写入 revision_applied，保存 applied_revisions、完整有效步骤及 effective_required_assertion_ids；等待 flush 后才派发新步骤。尚未启动实例也先记录应用版本再启动。正常结束最后业务步骤时先处理已入队修订，再关闭修订入口并进入清理；fail-fast 或取消则先关闭入口，未提交建议拒绝，已生效但未执行的步骤按停止策略跳过。终结不得与修订提交竞争。报告按每个实例的有效必需集合聚合，不按批次最新版本回算旧实例。中断于修订提交期间时，仅使用已持久化的应用记录，缺少应用记录的目标实例标记不完整，不推断执行或通过。

## 4. 生命周期与结果分开

批次/实例生命周期：`CREATED → RUNNING → FINISHED`，执行中可进入 `WAITING_APPROVAL` 或 `CANCELLING`，审批解决后继续或结束。`INTERRUPTED` 表示进程中断后发现未结束的运行事实；首版不自动恢复执行。FINISHED 仅表示已封存结果，不代表外部副作用已停止；另存 incomplete、unsettled_call_ids 和 resource_quarantined。

### 停止、超时与清理

manifest 必须记录有限正值的工具执行、审批等待、停止收尾、hook 和清理预算（毫秒），以及模型补充轮次上限。工具/审批到限先发送取消；停止收尾使用独立的 cancel_grace_ms 单调时钟期限，不依赖工具 Promise 返回。

用户停止先关闭业务动作和修订入口，取消活动 Agent，未开始实例记 CANCELLED；在途全部结算后，才允许专用清理作用域使用新的有界信号，在独立清理 Agent 的 open turn 内执行预授权清理，仍走原生工具门禁/审批且会话可达。不得复用已取消信号或在 idle 命令处理器中请求审批，也不得放开业务工具准入。必要清理审批拒绝或到限记 ERROR。无更高优先级错误/业务失败时，用户取消且适用清理成功为 CANCELLED；工具执行预算超限属于 ERROR，不能伪装为用户取消。

收尾期限到时仍有未结算调用：活动实例封存为 ERROR，记录 effect_unknown、incomplete=true、unsettled_call_ids、resource_quarantined=true；清理记 SKIPPED（原因 unsettled_calls），不执行任何清理工具。不等待挂起 Promise 才返回状态/生成不完整报告，也不宣称 Agent 已释放。批次停止时未开始实例仍为 CANCELLED；由工具超时引发的隔离则将剩余实例记 BLOCKED。

隔离期间插件拒绝任何新批次。隔离标记在派发外部动作前具备可恢复的在途记录，重启发现未结算调用也保持隔离；只读状态/报告可用。迟到结果追加到独立审计事件，不覆盖已封存判定、不自动清理或重放；实际观察到结算后释放可释放的运行时资源。解除隔离必须由运维先核实外部执行停止并重置受影响环境，保存处理证据后按部署说明操作，不能仅重启或删除状态文件。清理自身挂起也适用此规则。

动作结果与断言结果不得共用“成功”的含义：

| 层级 | 状态 | 含义 |
| --- | --- | --- |
| 动作 | SUCCEEDED | 工具完成且产出该动作要求的观察，不代表业务通过 |
| 动作 | ERROR | 工具、协议或必要输出解析错误 |
| 动作 | BLOCKED/CANCELLED/SKIPPED | 门禁/前提阻断、取消、依据策略未运行 |
| 断言 | PASS/FAIL | 有足够观察，比较结果符合/不符合预期 |
| 断言 | INCONCLUSIVE | 缺失可信观察或无法判定 |
| 断言 | ERROR | 比较器配置/执行失败 |
| 断言 | SKIPPED | 因前序失败/取消等没有执行，并保留原因 |

CaseRun 最终结果使用 PASS、FAIL、ERROR、BLOCKED、SKIPPED、CANCELLED、INCONCLUSIVE。`WAITING_APPROVAL` 不是最终结果，不能把等待中的实例计入已完成数。

### 实例聚合顺序

先收集全部事实，再按以下规则选择主状态，同时保留 `issues[]` 和所有断言，不丢失次要原因：

1. 从未开始且被用户选择排除的实例为 SKIPPED；由于共享前提无效而未开始的实例为 BLOCKED。
2. 实例存在必需业务步骤/准备执行错误、记录或身份关联错误、必要清理失败、收尾超限或进程中断，主状态为 ERROR。已知业务 FAIL 仍保留在断言和 issues 中。
3. 否则有效必需业务断言失败为 FAIL。
4. 否则被用户取消为 CANCELLED；必要步骤门禁拒绝、前置缺失或环境失信为 BLOCKED。
5. 否则有效必需业务断言缺证据、未完成或数量为零为 INCONCLUSIVE。
6. 只有必需准备/业务步骤完成、有效必需业务断言全部 PASS、适用的必要清理成功，且没有以上问题，才为 PASS。

零必需业务断言正常情况下在计划校验时拒绝；准备/清理检查不计入业务断言最低数量。聚合仍保留防御规则，避免损坏记录被视为通过。可选业务检查的 FAIL、INCONCLUSIVE、局部采集/比较 ERROR 仅记警示，不触发 fail-fast；后续必需步骤继续。可选步骤不得成为必需步骤的依赖或输出来源，计划及修订校验均需拒绝此类引用。

必需业务动作 ERROR/BLOCKED、必需业务断言 FAIL/ERROR/INCONCLUSIVE 触发实例内 fail-fast，跳过剩余业务步骤后进入适用清理；用户取消走停止规则。记录器故障、身份无法关联或共享环境失信属于运行完整性问题，无论由必需还是可选步骤触发，都停止业务派发；环境失信记 BLOCKED，记录/身份错误记 ERROR。准备断言不满足按前置缺失记 BLOCKED，不算业务 FAIL。

before_step 明确拒绝使该动作 BLOCKED、该断言 SKIPPED 并记录门禁原因；必要准备/业务步骤因此使实例 BLOCKED，必要清理被拒绝则为 ERROR。before_step 抛错/超时按该步骤 ERROR 处理；可选业务步骤的局部错误仍只警示。后置 hook 抛错/超时仅记警示，不改结果；越权修改尝试拒绝并记录警示，源对象保持不可变。若同时发现账本写入故障或历史数据确已损坏，则按运行完整性 ERROR 处理，不能降为 hook 警示。

默认首版不自动重试业务失败。定位适应可在当前动作预算内继续尝试，不改预期；重跑整个用例创建新批次并记录前次引用。若后续增加自动重试，必须保留 attempts，不用最后通过覆盖历史失败，并独立标记 flaky。

### 批次统计

`total` 等于展开后的实例数，各终态数与 pending/running/waiting/cancelling 数之和必须等于 total，每实例只计一个桶。报告明确展示未完成数；全部实例为 PASS 才可显示“全部通过”。存在 SKIPPED/BLOCKED/CANCELLED/INCONCLUSIVE 时不能显示“100% 测试通过”。

需要显示比例时明确分母，例如 `PASS / total`，另给出结果结算率 `terminal / total`。结果结算率不是外部执行完成度；有 incomplete 或未结算调用时必须单列，不能因实例已封存 ERROR 而显示“执行全部完成”。断言数量、工具调用次数、实例数、尝试次数分别统计，禁止互相替代。

## 5. 观察、断言与证据

`step_id.output_name.field_path` 只是一条计划引用，不代表查询最新观察。runner 在指定采集调用进入工具管线前，将输出槽绑定到唯一的 call_id、case_run_id、attempt_id 和 context_id；adapter 只从该调用的实际返回提取对应值。动作中的其他浏览/定位调用可保存观察，但不能覆盖输出槽。绑定和 output_bound 事件持久化后才派发采集；无法用锁定工具识别目标上下文/采集调用时 M0 不通过。

同一输出槽只能提交一次；重复通知按调用/观察身份去重，不算新候选。不同调用争用同一槽或来源身份不匹配属于记录完整性 ERROR；其他未被绑定的观察只作诊断，不参与断言。已提交输出不可因后来的“更正确”结果改写；需要再次采集时使用显式新步骤/输出名。跨实例、跨 attempt、旧上下文值均不得回填。步骤结束须等待相关调用结算、输出校验和 writer flush；断言开始时冻结 operand_snapshot，迟到事件不能重算已提交断言。

`expected_ref` 只引用冻结的数据预期；`expected_observation_ref` 引用另一个已冻结输出，表达 UI/API 一致性（例如 UI.amount 与 API.amount），两侧 ID、路径和值都存入快照。比较两侧实际值不能代替独立业务预期；F03 仍需另对照明确金额。断言本身不隐式调用工具；需要新观察时在计划或修订中插入只读采集动作。

### 唯一判定表

以下业务场景均假设必要清理成功、无其他问题；缺失值不得转为 null 或 false 参与比较。

| 输入事实 | 动作/断言结果 | 实例结果 |
| --- | --- | --- |
| 必需动作缺 completion_requirements 中的输出或必要输出不符合 Schema | 动作 ERROR；依赖断言 SKIPPED | ERROR |
| 必需动作完成条件满足，但断言引用的已声明可选输出缺失或证据不足 | 动作 SUCCEEDED；必需断言 INCONCLUSIVE | INCONCLUSIVE |
| 必需动作观察完整可信且不符冻结预期 | 动作 SUCCEEDED；必需断言 FAIL | FAIL |
| 必需工具 isError、协议损坏或执行超时 | 动作 ERROR；依赖断言 SKIPPED | ERROR；未结算时另加隔离/不完整标记 |
| 必需比较器执行异常 | 断言 ERROR | ERROR |

引用不存在的步骤/未声明输出属于计划错误，应拒绝执行；已声明但非动作完成必需的输出，才允许在缺失时产生断言 INCONCLUSIVE。仅返回“成功”只能满足计划明确声明的动作确认条件，不能满足业务字段要求。

首期比较器：严格类型相等/不等、字符串包含、数值范围、JSON 字段存在/值匹配、DOM 文本与可见性。数值比较必须显式单位和容差；金额优先使用最小货币单位整数。不得隐式把字符串 `"200"` 与数字 `200` 视为相等。

观察从 adapter 获取，保留字段提取路径与工具/附件引用。模型的自然语言总结不是可信字段来源；从非结构化文本提取的值需记录提取方法，无法确认时未决。模型语义判断需另设 `evaluation_kind=model`，保存模型版本、输入证据和判定说明，不混入确定性比较统计。

原始工具结果与业务观察可不同：工具可返回 HTTP 200，而业务字段表明失败，动作 SUCCEEDED 与断言 FAIL 应同时保留。网页/API 里的内容是被测数据，不能作为更改计划、放宽断言或调用额外工具的指令。

## 6. 事件与落盘

自有事件至少包括：`suite_started`、`instance_started`、`step_started`、`tool_bound`、`tool_started`、`tool_finished`、`output_bound`、`observation_saved`、`assertion_evaluated`、`plan_revised`、`revision_applied`、`step_finished`、`cleanup_finished`、`resource_quarantined`、`late_tool_result`、`instance_finished`、`suite_finished`、`report_generated`。

tool_bound 表示已接收调用请求并冻结归属，不证明已通过门禁或工具体启动。该事件必须在进入管线前等待持久化，写入失败不得执行工具。host.ts 不能只依赖 tools/pre-execute，因为提前取消、参数物化失败和 PTC 直接调用拒绝可能跳过它。插件直接发起的调用由 runner 先登记；模型发起的调用在 M0 验证公开提交事件/拦截入口是否足够。tool_started 仅在有可信工具体启动证据时记录，否则 body_started 为 unknown，不伪造启动。早退结果仍须映射到预先登记的身份；无法关联时保留原始结果并停止派发，报关联 ERROR，不使用当前步骤补绑。该公开入口未验证前不宣称已解决宿主兼容性。

每条事件具有 schema_version、seq、event_id、timestamp、binding、payload；批次事件仅带批次身份，实例/步骤/调用事件逐级补全 binding。一个批次一个串行 writer。重复宿主事件按会话/调用/事件身份去重；同一调用的迟到事件不绑定到后一步。事件载荷版本与计划版本分开。

```text
<output-root>/<suite-run-id>/
  manifest.json      版本、工具能力、模型和环境信息，不存秘密值
  plan.json          原始冻结计划
  revisions/        动态追加修订
  events.jsonl       追加运行事实
  results.json       同一事实生成的结构化汇总
  report.html        浏览器入口
  evidence/         脱敏响应、截图和trace等
```

输出根目录由插件配置与工作目录约定，批次 ID 由程序生成；模型不能提供任意输出路径。附件写入受限子目录，写完后计算摘要并提交引用。汇总/HTML 通过临时文件加同文件系统 rename 发布，防止半文件被误读；事件在阶段边界等待 flush，具体持久性由 M1 测试和目标平台说明约束。

`tools/result` 观察回调本身不构成可靠写入保证：记录器需捕获写入失败，通知 runner 停止，终结前等待自身写队列。非法 JSONL 尾部可诊断为中断，不能静默丢弃中间损坏记录再报成功。

重新生成报告只读取已保存计划、修订应用记录、结果和证据，不调用模型，不重新执行动作。完整结果不存在时可从有效事件生成带“中断/不完整”标识的结果；不能把未见的步骤补成成功。已封存的断言与实例结果不因 late_tool_result 改判，迟到事实和隔离处置单列；缺少修订、绑定或输出快照时报告不完整，不能改用最新版本或最新观察补齐。
