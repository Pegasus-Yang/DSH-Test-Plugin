# 实际步骤与手工用例

此功能位于主分支“未发布”更新，`v0.10.0` 标签暂不包含。

本功能随测试自动启用，不用填写新设置，也不用记住新命令。安装包含这项功能的插件、重启 DSH 并刷新页面后，照常使用 `/test`、`/test-plan`、`/test-run` 或 `/test-data`。

## 1. 先看一个例子

在 DSH 对话中输入：

```text
/test 访问ceshiren.com，搜索 agent，打开第一条搜索结果，断言帖子正文不为空
```

最初的计划可能只有“搜索 agent”。开始执行、看到了真实页面后，模型会说明当前需要做什么，再执行这个动作。最终报告可能出现：

| 序号 | 实际步骤 | 实际输入 | 本次记录 |
| --- | --- | --- | --- |
| 1 | 点击页面搜索按钮，展开输入区域 | 搜索按钮 | 工具执行成功 |
| 2 | 在搜索框中输入关键词 | agent | 工具执行成功 |
| 3 | 按 Enter 提交搜索 | Enter | 工具执行成功 |

这只是例子。如果页面一开始就有输入框，就不需要点击按钮，也不会补写那一步。导航、打开结果、最终检查同样会按实际发生顺序编号。每条说明旁边能看到它来自哪个原规划步骤。

## 2. 去哪里看

1. 等这次测试结束，点击对话里的“查看测试报告”。
2. 在报告左侧选择要查看的用例和数据实例。
3. 右侧有新记录时，默认打开“实际步骤”。从 1 开始，按顺序看操作和检查。
4. 想核对工具参数时，展开该行的“查看原生调用依据（脱敏）”。
5. 想看原计划、采集调整和完整工具记录时，切换“步骤”；断言、附件、操作录像也保留各自入口。

输入框上方的进度仍显示原规划步骤的进度与耗时。例如原计划有 4 步，搜索在运行时拆成 3 个动作，进度分母仍然是 4；报告展示这 3 个真实动作。它们解决的是两个不同层次的查看需求。

## 3. 保存成自己的手工用例

在当前实例的“实际步骤”上方点击：

- **下载手工用例 Markdown**：一份能阅读、能编辑的 `.md` 文件。保存后可以复制到自己的用例文档。
- **下载实际步骤 JSON**：一份结构化的操作与检查记录，适合后续工具读取。

报告概览和运行信息页还提供完整批次的两种下载。CSV 有多行时，每个实例分别保存数据和步骤，序号各自从 1 开始。

Markdown 包含任务、测试数据、原规划、前置条件、实际操作、原有预期、本次状态和收尾。请先读清楚，再作为手工测试参考。它记录的是本次实际路径，保留定位失败和重试；插件没有替你把它整理成“理想成功路径”，也没有重新跑一遍导出的文件。

**看到“待补充”时，自己补充预期。** 比如点击按钮成功，并不能证明“搜索框必定显示”这个业务检查已经做过。原任务没有独立规定或验证这个预期时，插件不会按照本次页面反推一个预期。

JSON 的 `format` 是 `dsh-actual-steps`，与执行计划不同。不要拿它直接交给 `/test-run`；如果要重新执行，使用原用例文件或原任务。

## 4. 怎样理解状态

| 提示 | 你应该怎样理解 |
| --- | --- |
| 工具执行成功 | 原生工具成功结算；业务是否符合要求，继续看检查行 |
| 检查通过 / 检查失败 | 使用原有可信观察和冻结预期得到的比较结果 |
| 工具执行异常，结果需复核 | 工具报错；外部系统可能已经发生部分变化，不能简单当成“什么也没做” |
| 结果未知，需复核 | 取消、超时或中断后，没有拿到能够确认结果的记录 |
| 未执行的说明 | 操作被拒绝或在派发前取消，放在附录，不占主要序号 |
| 复合操作 | 脚本或一次多动作工具；内部每个动作还没有逐条确认 |

“实际步骤说明完整性”独立于测试结果：

- `COMPLETE`：已保存的操作说明及关联完整。出现检查失败时，测试仍然可能是 FAIL。
- `PARTIAL`：存在未知结果、复合操作、未逐项确认的直接分析脚本、未完成规划或记录问题，需要复核。
- `NOT_RECORDED`：旧运行没有这项记录。旧报告继续打开原“步骤”页，不让模型事后编一份操作说明。

准备和业务收尾在独立区域。页面快照、内部截图采集、插件自动浏览器复位与关闭不会占业务步骤编号。相同动作重试两次会保留两次，方便知道第一次为什么失败。

## 5. 接口用例是什么样

GET JSON 用例会记录“发送 GET 请求并采集响应”，显示真实 URL，随后列出检查行。一次真实请求不会因为多个字段检查被重复算成多次请求。

纯接口实例不展示浏览器操作、页面截图占位或录像入口；混合批次也按每个实例各自的数据展示。当前可信接口采集仍只支持 GET JSON。

## 6. 文件在哪里，丢了怎么办

每次运行的输出目录包含：

```text
run-…/
  plan.json
  results.json
  events.jsonl
  actual-steps.json
  manual-cases.md
  report.html
  evidence/
```

运行目录位置可以在最终回复或报告中找到。新文件与原报告的数据来自同一份已保存、已脱敏的运行事实。

文件导出失败、文件丢失或需要重新生成时，等运行结束后点击进度区的“重建报告”，或者进入“设置 → 测试插件 → 测试报告”，填写运行 ID 后重建。得到：

```text
actual-steps-rebuilt.json
manual-cases-rebuilt.md
results-rebuilt.json
report-rebuilt.html
```

原文件保持原样。重建只读取已保存的账本，不调用模型、不打开目标页面、不补执行。如果账本本身没有操作说明，就无法凭空找回来。

离线 HTML 中也可以下载文本文件；观看录像时仍需复制整个运行目录。操作参数和说明沿用既有脱敏规则。页面截图和录像仍包含实际页面内容，保存或分享时按自己的页面内容处理。

## 7. 常见问题

| 现象 | 处理办法 |
| --- | --- |
| 刚更新后没有“实际步骤” | 卸载旧包、安装新包、重启同一 profile 的 DSH 并刷新页面，然后新跑一次；旧运行不会补出记录 |
| 看到一次定位失败和一次成功 | 正常保留了真实重试；保存为手工用例前自行复核是否需要调整文档 |
| 每行都显示“待补充” | 这些行没有独立检查；继续看后面的检查行，再补充手工用例需要的中间预期 |
| 模型提示要使用 `test_execute_operation` | 这是插件给模型的内部入口要求，不是给用户的新命令；让当前对话继续完成即可 |
| 取消后有“结果未知” | 先确认外部操作停止；需要释放环境时按[测试环境卡住怎么办](测试环境卡住怎么办.md)处理，不把未知动作当作成功 |
| 输出文件失败但断言有结果 | 使用已保存账本重建；文件导出失败不改写原断言结果 |

实现和验收边界见[当前实现](../architecture/当前实现.md)及[实施方案](../design/运行实际步骤与手工用例导出实施方案.md)。
