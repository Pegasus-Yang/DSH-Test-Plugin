## 以后发布时怎么做

1. 每次重要版本交付（核心功能新增、重要优化或重大缺陷修复）必须更新 `package.json` 的版本号，同时更新运行记录的 `plugin_version` 和受影响的文档；将根目录[更新日志](../../changelog.md)的本版“未发布”条目归入对应版本，填写交付提交日期与标签链接。版本号和本地附注标签须在交付收尾完成，不等到推送时再补；常规开发提交不逐次发版。
2. 按改动完成类型检查、构建、相关测试及必要的真实安装验收；构建、测试和打包方法见[安装与运维](安装与运维.md#构建与打包)。0.9.1 起，提交重建的 `dist`，用 `pnpm verify:package` 核对清单入口，并在没有宿主源码链接的环境核对重建产物一致；验收 Git 来源安装、停用和卸载后 MCP 正常工作。
3. 提交该版本全部实现和验收文档。确认工作区没有遗漏的待发布文件，再在最后交付提交上打附注标签。只有全部内容确认后才打标签。
4. 默认由用户审核后手动把交付提交及本次版本标签推到已有发布远端；用户明确授权本次推送时按授权执行。不要使用强制推送，也不要顺带推送其他标签。
5. 核对标签的目标提交、包版本和远端结果。0.9.1 起可直接使用含 `dist` 的 Git 标签安装；Git标签不自动生成 tgz 或 GitHub Release，本地 tgz 仍按构建流程生成。

例如，已完成并提交一个新版本后，在项目根目录执行：

```sh
git status --short
release_version=$(node -p "require('./package.json').version")
git tag -a "v${release_version}" -m "发布 dsh-test-plugin ${release_version}"
git show "v${release_version}:package.json"
git rev-parse "v${release_version}^{commit}"
git push origin main
git push origin "refs/tags/v${release_version}"
git ls-remote --tags origin "refs/tags/v${release_version}" "refs/tags/v${release_version}^{}"
```

示例沿用当前 `origin/main`；采用其他发布分支时使用对应分支。附注标签有“标签对象”和“提交对象”，远端输出中带 `^{}` 的一行才是目标提交，须与本地 `git rev-parse` 输出一致。已经存在相同标签时先核对，不用 `-f` 覆盖。

## 怎样找某个版本

列出版本、查看对应提交或比较两个版本：

```sh
git tag --list --sort=version:refname
git show --no-patch v0.8.3
git log --oneline v0.8.2..v0.8.3
git diff v0.8.2 v0.8.3
```

在GitHub仓库的Tags页面也能按版本查找。其他本地克隆第一次需要读取这些远端标签时，执行 `git fetch origin --tags`。临时查看旧版可执行 `git switch --detach v0.8.2`，查看后用 `git switch main` 返回；操作前先提交或暂存当前改动，避免把自己的工作夹在旧版里。
