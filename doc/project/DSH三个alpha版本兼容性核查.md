# DSH三个alpha版本兼容性核查

[文档导航](../README.md) · [多版本兼容方案](../design/DSH多版本兼容方案.md) · [既有宿主升级验收](DSH宿主升级适配验收.md) · [公开依赖安装验收](CI公开依赖安装验收.md)

## 核查对象与结论边界

2026-10-17 核查提交 `2e769342b9a9aa7b9d97fea69f0bc9875b777298` 的插件 `0.12.3`，目标宿主为 DSH `0.2.1-alpha.1`、`0.2.1-alpha.2`、`0.2.1-alpha.3`。正式源码、依赖清单、锁文件、`dist` 和标签保持原样；本轮交付核查记录与兼容方案。

**当前发行包的正常支持声明只有 alpha.3。** 原包在 alpha.1、alpha.2 的实际宿主中被明确跳过，原因是 22 个 DSH peer 精确指定 alpha.3。三版公开 SDK 的类型检查和各 363 项回归通过；在独立副本中仅放宽 peer，三版宿主均可在没有豁免的情况下组合出插件条目。运行行为验证与正式发包准入须分别判断。

同一原包随后在三个真实宿主上完成统一 Markdown 网页、接口正例与接口反例，共 9 轮运行；网页和正例通过，反例按固定错误预期得出 FAIL。9 份账本与 46 份原始证据校验通过，三个宿主的验收页面均无脚本错误。本轮覆盖的核心链路未发现需要新增运行时版本分支的 API 差异，首次改造可以优先调整准入元信息和验证门禁。

各组 DSH 包的实际版本全部等于本组宿主版本，没有跨组混装。环境为 macOS arm64、Node.js `22.22.3`；宿主安装到 `/private/tmp/dsh-multi-version-20261017/` 下的三个独立目录，与项目及本机 DSH 源码没有祖先依赖关系。

安装使用公开 npm 包，以官方标签中的包版本生成同批依赖覆盖约束，固定 DSH 与基础框架版本；保留各环境的安装锁文件。它证明对应公开 SDK 组合的兼容性，不能写成未经约束的任意 npm 解析结果均已验证。插件 tgz 通过 npm 安装到独立 profile，使用真实 DSH CLI 加载；本轮没有把 `dsh plugin add` 安装器路径作为新验收结论。

宿主的模型、会话、工作区、运行输出和浏览器配置均放在临时 profile 或本机忽略目录，未修改用户正在运行的 DSH、GitLab、RunBridge 或其他项目。本轮未执行 GitLab 业务写操作。

### 同一个发行包

从当前工作树使用 `npm pack --ignore-scripts` 生成一次 tgz，SHA-256 为：

```text
9692a47eb5ef7af022be99b3f2bac997f364b3daf04b620deecfad905790d39c
```

三个 profile 中的 95 个 `dist` 文件逐一与该 tgz 比较，内容一致；profile 内没有 DSH SDK 副本，运行 SDK 由对应宿主提供。没有为旧宿主重新编译插件，也没有使用 `link:host`。

回归使用当前提交的源码、测试和已提交 `dist` 副本，SDK 来自各自公开安装目录。测试命令为：

```sh
node ../node_modules/typescript/bin/tsc --noEmit
node ../node_modules/vitest/vitest.mjs run tests/unit tests/integration \
  --maxWorkers=1 --minWorkers=1 --reporter=json
```

首轮并行运行出现两个集成用例及一项账本规模检查失败；相关集成用例单独运行通过，随后限制为单 worker 的完整回归在三个版本均通过，未调整生产超时或修改测试。初次临时环境缺少测试所需的 Playwright、React 开发依赖，补齐后才执行最终检查；缺依赖结果不归为 SDK 不兼容。

## 真实宿主与 Markdown 运行

原包在旧宿主上无法正常加载，因此运行行为实验只向 alpha.1、alpha.2 的临时 profile 授予 `dsh-test-plugin@0.12.3` 对应精确宿主版本的豁免。alpha.3 无豁免。原包内容保持一致，探针和固定页面均为验收配置的一部分，不进入发行包。

验收通过真实浏览器输入 Markdown 命令、原生模型与 Agent Loop、Playwright MCP、可信 HTTP 采集和最终报告执行；没有直接提交模型编造的实际值。私有模型配置仅在本机复用，未写入本次提交。

固定用例包括：

| 用例     | 固定输入与预期                                           | 验证目的                                                          |
| -------- | -------------------------------------------------------- | ----------------------------------------------------------------- |
| 网页     | 本地只读页面存在账号输入框、密码输入框和“登录”按钮       | Markdown 计划、关闭审核、重新提交批准、真实 DOM、同会话收尾及报告 |
| 接口正例 | GET 本地 `/api/amount`，固定响应种子为数值 101，预期 101 | 可信响应、字段绑定和 PASS                                         |
| 接口反例 | 同一接口，预期固定为 100                                 | 保留 101 的实际值并得出 FAIL，不能按实际响应反推预期              |

网页用例将“浏览器生命周期由插件负责”放在 Markdown 背景中，业务步骤只检查三个元素。关闭审核后要求无冻结计划、无业务实例、不自动重开；重新提交并批准后才执行。每轮生成报告后还检查 Agent 空闲、测试作用域关闭、在途调用排空，再启动下一轮。

| 固定配置复验                                     | alpha.1            | alpha.2             | alpha.3            |
| ------------------------------------------------ | ------------------ | ------------------- | ------------------ |
| 原包运行前提                                     | 临时精确版本豁免   | 临时精确版本豁免    | 无豁免             |
| 插件客户端与设置入口                             | 通过               | 通过                | 通过               |
| 关闭审核后无冻结、无实例、不重开；重新批准后执行 | 通过               | 通过                | 通过               |
| 网页三个元素检查                                 | PASS               | PASS                | PASS               |
| 接口实际 101、预期 101                           | PASS               | PASS                | PASS               |
| 接口实际 101、预期 100                           | FAIL，符合反例预期 | FAIL，符合反例预期  | FAIL，符合反例预期 |
| 原会话执行与清理、零资源隔离                     | 通过               | 通过                | 通过               |
| Agent 空闲、作用域释放后连续运行                 | 通过               | 通过                | 通过               |
| 认证报告打开、页面脚本错误                       | 通过，0 错误       | 通过，0 错误        | 通过，0 错误       |
| 账本、原始证据、冻结预期与断言完整性             | 3 轮／8 份证据通过 | 3 轮／29 份证据通过 | 3 轮／9 份证据通过 |

调用现有 `scripts/validate-report.mjs <运行目录> --data-only` 对 9 轮分别核对账本重建、证据 SHA-256、真实采集来源和确定性断言，并独立确认接口实际值 101 与预期 101／100。所有检查通过；报告在浏览器打开，网页和反例截图另作可视检查。各运行结束后均确认 Agent 空闲、作用域关闭和零在途调用，再启动下一轮。

完整结果保存在 `artifacts/validation/dsh-multi-version/summary.json`；正式发布仍须完成下节列出的门禁。

### 保留的失败与驱动修正

1. 首轮 alpha.1 网页运行的三个页面断言和框架清理均成功，但模型把用户文字中的关闭浏览器另拆为业务步骤，随后无法为已关闭页面补采而自行提交 ERROR。原实例结果未改写。后续三版统一使用业务边界明确的 Markdown，三个固定预期不变。
2. 驱动最初只等待报告 `FINISHED`，随后立即启动下一用例，触发共享测试互斥拒绝；只读探针确认旧实例随后正常关闭。修正驱动，等待 `closed`、Agent `idle`、`whenIdle` 完成和零在途调用。
3. 运行中加入诊断配置触发了 HMR，部分探索运行被记录为插件卸载中断。这些运行保留为环境中断，不能算作正常通过或 SDK 不兼容。最终复验使用新的 profile 和输出目录，启动前固定探针与配置并关闭 HMR；未清除旧运行的错误或隔离证据。
4. alpha.1、alpha.2 的设置位于旧版导航底部，alpha.3 使用账号菜单。驱动按实际入口操作，未因此修改插件客户端。

这些修正用于明确验收前提，不能据此推断生产环境永远不会发生模型规划错误、热重载中断或快速重复启动。

## 发布前还需要完成的验证

本轮核查用于判断三个版本的兼容可行性。它不把当前 `0.12.3` 改成正式多版本发行包，也不移动既有标签。正式交付至少还需：

- 按方案更新支持声明后，不使用豁免执行三版安装、启用、停用、卸载与重启。
- 在可编辑 profile 中核对设置和 MCP 参数的真实持久化；本轮设置入口可加载不代表所有配置写入已验收。
- 补齐停止、在途调用、未知状态隔离、恢复、同会话再运行和普通聊天资源清理的真实宿主场景。
- 按项目约定执行 Markdown GitLab UI 与接口回归；本地页面和 API 不能替代 GitLab 业务验收。
- 对 RunBridge 实机、Browscreen 预览和录像按既有功能边界执行对应验证；三版 SDK 回归通过不代表这些外部系统都已逐版重验。
- 让 Linux CI 消费同一候选 tgz 完成三版矩阵，再同步当前中英文文档、包版本、运行版本和本地附注标签。
