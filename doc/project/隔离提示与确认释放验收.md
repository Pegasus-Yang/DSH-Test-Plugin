# 隔离提示与确认释放验收

日期：2026-10-04。版本：0.8.1（开发版本）。本次处理隔离导致 `/test` 静默失败的问题，不修改 DSH 核心、旧测试结果或原有确定性断言。

## 实现与边界

- 独立只读 `/test-recovery` 路由沿用宿主认证，输入框上方持续显示原因、持续时间与遗留运行；不依赖已有测试步骤或聊天消息。
- 复用 `cleanupTimeoutMs`，默认 60000 毫秒。达到阈值提示“可能异常卡住”；同一遗留运行被重复识别时保留隔离起始时间，不按时间自动解除。
- 用户先确认旧外部操作停止，再经原生命令 `/test-recover --confirm <当前编号>` 调用专用 Playwright 的关闭工具和本插件预览收尾。关闭成功后保存 `release-*.json`，再解除同一记录。
- 编号绑定隔离文件摘要，过期确认或处理中被替换的记录不能解除新的隔离。活动测试、启动准备和在途释放保持互斥。
- 失败、审批拒绝、取消和超时均保留隔离并显示结果；超时及时返回，但后台在途操作未结算前继续互斥，迟到成功不能删除标记。
- 时间/记录异常、缺少资源归属、API/App 等无法确认浏览器资源的情形，保留实际外部处置和 `/test-release` 路径。
- 旧结果保持原样，不自动重放旧任务；原 CDP/首帧浮窗门禁不变。

## 验证

类型检查和构建通过；135 项单元/集成检查通过，覆盖超时边界、不自动关闭、起始时间保留、旧确认拒绝、并发互斥、原生关闭成功、关闭失败、取消、超时与迟到结果、旧账本保留、手工合同、只读路由和原生命令派发。

真实 DSH 0.2.1-alpha.1 验收使用独立 home/profile、13411 端口和专用 MCP 0.0.68。通过临时验收命令启动真实本地浏览器，再写入明确标记为夹具的历史隔离记录；不是正式业务测试，也没有派发模型任务。

| 检查 | 结果 |
| --- | --- |
| 没有聊天或测试步骤的新会话 | 显示原因、持续时间、1 分钟阈值和处理入口 |

真实界面验证发现前端原生命令依赖需要同时声明 `remote` 和 `remote.commands`，仅普通对象替身不能发现这个问题。已修正依赖并增加真实 Cordis 上下文的回归检查；重载后完整关闭链路通过。

当前用户默认 Web profile 已通过公开 CLI 更新到 0.8.1，并在确认无活动测试后正常重启 3080 服务。用户 Chrome 的新会话已显示实际遗留隔离的原因、持续时间和“处理并释放”入口；设置文件与原 `quarantine.json` 的摘要在更新前后相同。本次没有替用户确认或释放真实隔离，也没有重跑社区用例。当前服务为后台进程，本机 PID、认证地址和日志仅保存在忽略的 `.local/user-dsh-recovery-state.json` 与 `.local/user-dsh-recovery.log`；需要停止时可核实该 PID 后正常终止，再按原终端方式启动。

证据保存于忽略目录 `artifacts/validation/recovery/`：测试 JSON、`web-verification.json`、`user-profile-verification.json`、提示/确认/完成及当前用户提示截图，以及 `runs/` 中的夹具与处置记录。图文操作说明见[测试环境卡住怎么办](../user-guide/测试环境卡住怎么办.md)。关闭失败、取消和迟到返回等故障由回归替身覆盖，本次没有在用户真实浏览器中人为制造这些故障。
